9. Wir machen ein Repository, also ein Verzeichnis, der Produkte als internen CRUD Container.

using SecureCatalog.Api.Models;

namespace SecureCatalog.Api.Repositories;

public interface IProductRepository
{
    Task<IReadOnlyList<Product>> GetAllAsync(
        CancellationToken cancellationToken = default);

    Task<Product?> GetByIdAsync(
        int id,
        CancellationToken cancellationToken = default);

    Task<Product> CreateAsync(
        Product product,
        CancellationToken cancellationToken = default);

    Task<bool> UpdateAsync(
        Product product,
        CancellationToken cancellationToken = default);

    Task<bool> DeleteAsync(
        int id,
        CancellationToken cancellationToken = default);
}

Der Controller selbst wird später über das Interface auf unsere Repository Instanz zugreifen.

10. Der Controller, ziemlich einfach.
Mit Primary Constructor und Dependence Injection bekommen wir direkt eine Instanz des Repository mit DB Zugriff.
Wir verzichten beim POST und PUT auch auf die das interne Modell mit EF Anbindung und verwenden lieber DTO Records, um nur Payloads zu haben, die wirklich änderbar sind. Beide Methoden liefern als Ergebnis aber immer das komplette aktualisierte Objekt.

using Microsoft.AspNetCore.Mvc;
using SecureCatalog.Api.Contracts;
using SecureCatalog.Api.Models;
using SecureCatalog.Api.Repositories;

namespace SecureCatalog.Api.Controllers;

[ApiController]
[Route("api/[controller]")]
public sealed class ProductsController(
    IProductRepository repository)
    : ControllerBase
{
    [HttpGet]
    public async Task<ActionResult<IReadOnlyList<Product>>> GetAll(
        CancellationToken cancellationToken)
    {
        var products =
            await repository.GetAllAsync(cancellationToken);

        return Ok(products);
    }

    [HttpGet("{id:int}")]
    public async Task<ActionResult<Product>> GetById(
        int id,
        CancellationToken cancellationToken)
    {
        var product =
            await repository.GetByIdAsync(id, cancellationToken);

        if (product is null)
        {
            return NotFound();
        }

        return Ok(product);
    }

    [HttpPost]
    public async Task<ActionResult<Product>> Create(
        [FromBody] ProductRequestDTO request,
        CancellationToken cancellationToken)
    {
        var product = new Product
        {
            Name = request.Name,
            Description = request.Description,
            Price = request.Price
        };
            
        await repository.CreateAsync(product, cancellationToken);

        return CreatedAtAction(
            nameof(GetById),
            new { id = product.Id },
            product);
    }

    [HttpPut("{id:int}")]
    public async Task<ActionResult<Product>> Update(
        int id,
        [FromBody] ProductRequestDTO request,
        CancellationToken cancellationToken)
    {
        var existingProduct =
            await repository.GetByIdAsync(id, cancellationToken);

        if (existingProduct is null)
        {
            return NotFound();
        }

        existingProduct.Name = request.Name;
        existingProduct.Description = request.Description;
        existingProduct.Price = request.Price;

        await repository.UpdateAsync(existingProduct, cancellationToken);

        return Ok(existingProduct);
    }

    [HttpDelete("{id:int}")]
    public async Task<ActionResult> Delete(
        int id,
        CancellationToken cancellationToken)
    {
        var existingProduct =
            await repository.GetByIdAsync(id, cancellationToken);

        if (existingProduct is null)
        {
            return NotFound();
        }

        await repository.DeleteAsync(existingProduct.Id, cancellationToken);

        return NoContent();
    }
}

11. Authentication → Authorization → Permissions/Policies

Bedeutet JWT + Claims + Policy-basiertes Authorization-Konzept
JWT für Authentication
Claims für Authorization
Permissions/Policies für API und Zugriffskontrolle

- Wir legen eine statische Klasse an, wo wir für die verschiedenen Controller sogenannte Permissions definieren, die dem Anwender erstmal eine Berechtigung erteilen.
Später erstellen wir dann daraus Policies für die einzelnen Methoden, also Permission >> Policy!

- Wir machen unsere Permissions als Policy der Anwendung bekannt in der program.cs. 
Theoretisch könnte man auch User Rollen ("Admin", "User", etc.) verwenden, nur endet man dann schnell in einer "Hölle" wenn es um explizite Rechte geht.
Also lieber gleich detailliert über Permissions und Policies.

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy(
        Permissions.Products.Read,
        policy => policy.RequireClaim(
            Permissions.ClaimType,
            Permissions.Products.Read));

    options.AddPolicy(
        Permissions.Products.Write,
        policy => policy.RequireClaim(
            Permissions.ClaimType,
            Permissions.Products.Write));

    options.AddPolicy(
        Permissions.Products.Delete,
        policy => policy.RequireClaim(
            Permissions.ClaimType,
            Permissions.Products.Delete));
});

Meine Practice heute:

- Windows Docker App installieren, für WSL2 einrichten (siehe Google)

- docker in der bash direkt bauen lassen

Hier hilft es, die konkrete IP des WSL2 Linux zu verwenden (hostname -I).

13. Tests

Für unseren Fall macht es durchaus Sinn, den Controller zu prüfen, ob die Methoden sich so verhalten wie zu erwarten.

Wir nutzen dazu ein klassisches xunit Testprojekt, was wir aber gleich mal mit 2 Paketen erweitern.

dotnet new xunit -n SecureCatalog.Api.Tests
dotnet package add moq
dotnet package add Microsoft.AspNetCore.Mvc.Testing

moq hilft uns das Product Repository zu simulieren, ohne auf die echte Datenbank zugreifen zu müssen. 
Wir erstellen ein Repository auf Basis unseres Interfaces und sagen gleichzeitig, welche Methode welche Parameter erhält und was zurückgegeben werden soll.
Hier mal direkt als Beispiel:

        var repository = new Mock<IProductRepository>();
        
        repository
            .Setup(r => r.GetByIdAsync(42, It.IsAny<CancellationToken>()))
            .ReturnsAsync((Product?)null);

Am Ende erzeugt man den Controller mit dem repository.Object und kann dann testen, ob die Methoden das liefern, was sie sollen.

Das 2. Paket, mvc.Testing im AspNet.Core Umfeld kann uns helfen, easy alle Service API Methoden zu testen.

Das Grundgerüst ist sehr simpel:

using System.Net;
using Microsoft.AspNetCore.Mvc.Testing;

namespace SecureCatalog.Api.Tests.Integration;

public class AuthorizationTests : IClassFixture<WebApplicationFactory<Program>>
{
    private readonly HttpClient _client;

    public AuthorizationTests(WebApplicationFactory<Program> factory)
    {
        _client = factory.CreateClient();
    }
}

IClassFixture<WebApplicationFactory<Program>> hilft uns, einfach den gesamten WebService zu erzeugen und zu verwenden.

Ab jetzt können wir ganz einfach wieder mit [Fact] Tests hinzufügen.

ABER, unser Problem ist, das der WebService ja auf einer DB beruht, die beim Deploy nicht existiert, also müssen wir ein Inmemory DB erzeugnen und nutzen.

Dazu brauchen wir auch SQLite im Test Projekt:

dotnet package add Microsoft.EntityFrameworkCore.Sqlite

Dann können wir eine eigene Factory schreiben, die die DB inmemory erzeugt.

Leider kollidiert so ein Test mit dem Production WebService, weil wir eine Migration laufen lassen, bevor bzw. wenn die TestApp hochkommt.

Wir sollen also generell prüfen, am besten in der program.cs, ob wir in einem Testszenario sind und entsprechenden Code nur bedingt ausführen.

In unserem Fall konkret (in der WebApi Source, nicht im Test Projekt):

if (!app.Environment.IsEnvironment("Testing"))
{
    // make sure db is exists and migrated on startup
    using (var scope = app.Services.CreateScope())
    {
        var db = scope.ServiceProvider.GetRequiredService<CatalogDbContext>();
        await db.Database.MigrateAsync();
    }
}

"Testing" setzen wir unserem Testcase Szenario, so das die die "Life" App nicht gestört wird. Das machen wir in unser eigener Factory, die wir ja schon für den inmemory Part brauchen.

protected override void ConfigureWebHost(IWebHostBuilder builder)
{
    builder.UseEnvironment("Testing");
    ...
}
